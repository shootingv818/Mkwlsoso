جمله‌ی «علت» بر اساس خطا عوض می‌شود:

| خطا | جمله |
|---|---|
| FLOOD | ایتا موقتاً محدودیت گذاشته → **۶۰ دقیقه** دیگر (عدد واقعی سرور) |
| کد اشتباه/منقضی | کد درست نبود یا منقضی شد. دوباره شروع کن و کد تازه را سریع بفرست |
| تایم‌اوت ۳۲۰ ثانیه | کد را به‌موقع نفرستادی، لغو شد |
| رمز دومرحله‌ای غلط | رمز دومرحله‌ای درست نبود |
| `no_hash` / `sendCode` | ایتا الان کد نداد. کمی بعد امتحان کن |
| شماره ثبت‌نشده | این شماره روی ایتا ثبت نیست |

## ۵-۲) قواعد

۱. **یک رویداد = یک عنوان یکسان + یک کد پیگیری یکسان** در هر دو نسخه.
۲. **کارت لاگ همیشه اَبَرمجموعه‌ی کارت مشتری است.**
۳. **مشتری هرگز نمی‌بیند:** پاسخ خام سرور، نام موتور، زمان مراحل، مسیر فایل، آمار
   ناوگان، وجود مشتری‌های دیگر.
۴. **مشتری همیشه می‌بیند:** کد پیگیری، و کاری که باید بکند.
۵. **شماره همه‌جا ماسک** (`98916***736`) — پیوی مشتری و گروه لاگ. کامل فقط پنل مالک.
۶. **کارت لاگ همیشه دارد:** کد پیگیری · مشتری (نام + آیدی) · شماره · زمان.
۷. **کارت‌های زنده در جا ویرایش می‌شوند**، با `msg_id` ذخیره‌شده تا بعد از ری‌استارت
   ادامه بدهند نه از نو.
۸. **هرگز per-recipient لاگ نمی‌شود.**

## ۵-۳) یک تابع، دو خروجی

```
emit(event, customer_id)
   ├─ گروه لاگ  : کارت کامل
   └─ پیوی مشتری: نسخه‌ی امن (اگر داشته باشد)
```
کد پیگیری همان‌جا **یک بار** ساخته می‌شود تا در دو نسخه یکی باشد. اگر این منطق پخش
باشد، یک روز یک کارت کامل اشتباهاً به مشتری می‌رود.
