### ۲-۱) سهمیه روی **افزودن اکانت** است، نه ارسال

این نکته مهم است چون در نسخه‌های قبلی این سند اشتباه ثبت شده بود.

> هر مشتری در هر ۲۴ ساعت حداکثر **۱۰ اکانت** می‌تواند اضافه کند. وقتی به ۱۰ رسید و
> دوباره «افزودن اکانت» را زد، ربات **درباره‌ی محدودیت توضیح بدهد** — نه اینکه فقط
> ردش کند.

پیام پیشنهادی:
```
⏳ سهمیه‌ی امروزت پر شد

امروز ۱۰ اکانت اضافه کردی که سقف روزانه است.
سهمیه‌ی بعدی : ۶ ساعت و ۲۰ دقیقه دیگر
اکانت‌های فعلی : ۲۳ از ۴۰
```

**چرا این طراحی درست است:** افزودن اکانت گران‌ترین کار سیستم است — هر لاگین یک مرورگر
کروم را تا ۳۲۰ ثانیه اشغال می‌کند. ارسال با موتور سریع **هیچ مرورگری مصرف نمی‌کند**. پس
سهمیه دقیقاً روی همان چیزی گذاشته شده که کم و گران است.

و اعداد با هم جور هستند: ۱۰ اکانت در روز × ۴ روز = ۴۰ اکانت، یعنی همان سقف کل.

**پنجره غلتان است، نه تقویمی.** «هر ۲۴ ساعت» یعنی الگوی `usage_daily` پروژه‌ی مرجع
(که کلیدش رشته‌ی تاریخ است و نیمه‌شب ریست می‌شود) **کار نمی‌کند**. پیاده‌سازی درست:
زمانِ ۱۰ افزودن آخر هر مشتری ذخیره شود؛ افزودن یازدهم فقط وقتی مجاز است که
قدیمی‌ترینِ آن ۱۰ بیش از ۲۴ ساعت عمر داشته باشد. این هم دقیق است و هم زمانِ آزادشدن
سهمیه‌ی بعدی را می‌دهد تا در پیام بالا نشان داده شود.

**پیامد: ارسال سقف روزانه ندارد.** تنها ترمزهای ارسال اینهاست: سقف ۴۰ اکانت، تعداد
مخاطبین، صف پذیرش مرورگر، و محدودیت‌های خودِ ایتا.

### ۲-۲) بدون مهاجرت داده

این سرویس یک **پروژه‌ی مستقل** است و به سرور و اکانت‌های فعلی مالک ربطی ندارد. پس:

- دیتابیس از صفر ساخته می‌شود، `PROFILES_DIR` خالی شروع می‌شود.
- **هیچ اسکریپت مهاجرتی لازم نیست** — که ریسک‌دارترین بخش فاز ۱ را حذف می‌کند.
- مالک هم اگر اکانتی خواست، مثل بقیه اضافه می‌کند.

## ۳) دو موتور — کلید failover مالک

### چه هستند

| نام فارسی | معادل فنی | چطور کار می‌کند |
|---|---|---|
| **موتور مرورگر** | `bridge` | ربات یک کروم باز می‌کند، وارد وب ایتا می‌شود، از داخل همان صفحه می‌فرستد. کند و سنگین (هر کروم ~۱ گیگ رم) ولی **پشتیبان per-recipient دارد** |
| **موتور سریع** | `hybrid` + `browserless` | ربات مستقیم با HTTPS به ایتا وصل می‌شود، **بدون هیچ مرورگری**. خیلی سریع‌تر، صفر رم، ولی **پشتیبان ندارد** |

موتور سوم `direct` در کد می‌ماند ولی **در UI نشان داده نمی‌شود** — همان hybrid است
منهای شبکه‌ی ایمنی، و `effective_engine()` هم اگر `MKWL_ENABLE_DIRECT=1` نباشد خودش
تنزلش می‌دهد. نگه‌داشتنش در منو فقط یک تله است.

### کلید انتخاب — طراحی نهایی

> **کلید در تنظیماتِ سمت مالک است و تعیین می‌کند همه‌ی مشتری‌ها با کدام موتور کار
> کنند. یک انتخاب برای همه. اگر یک موتور خراب شد، مالک سویچ می‌کند به بعدی. مشتری
> این کلید را نمی‌بیند و نمی‌تواند عوضش کند.**

یعنی یک **کلید failover** است، نه تنظیم سلیقه‌ای. پس: **گلوبال، نه per-customer.**

سه رفتار اجباری:

۱. **سویچ روی جاب‌های در حال اجرا اثر نگذارد.** هر جاب تنظیماتش را در لحظه‌ی شروع
   می‌گیرد؛ جاب جاری با موتور خودش تمام می‌شود و فقط جاب‌های **جدید** موتور تازه را
   می‌گیرند. عوض‌کردن موتور وسط یک ارسال، ریسک تکرار یا گم‌شدن پیام دارد.
۲. **سویچ مرورگرهای گرم را می‌بندد.** کلید pool شامل مسیر init-script است، پس تعویض
   موتور سشن‌های گرم را دور می‌اندازد. دکمه باید این را بگوید.
۳. **تنزل امن.** `effective_engine()` از قبل روی مقدار نامعتبر به `bridge` برمی‌گردد،
   یعنی حالت پیش‌فرضِ خرابی همان امن است.

### هشدار خودکار

کلید دستی فقط وقتی کار می‌کند که مالک نگاه کند. اگر موتور سریع نصف شب خراب شود
(توکن باطل، کانتکست کهنه)، تا مالک بفهمد چند مشتری ارسال ناموفق دارند — و موتور سریع
**پشتیبان ندارد**، پس آن ارسال‌ها واقعاً از دست می‌روند.

| مورد | تصمیم |
|---|---|
| هشدار در گروه لاگ بعد از N شکست پیاپی | **روشن** — فقط یک پیام، ضرری ندارد |
| تنزل **خودکار** به موتور مرورگر | **خاموش** — تصمیم دست مالک است |

زیرساختش هست: `MAX_CONSECUTIVE_FAILURES` همین منطق را برای یک جاب پیاده می‌کند؛ اینجا
باید در سطح **موتور** شمرده شود نه جاب.

## ۴) کارت‌ها و مسیرشان

### قاعده
کارت‌های عادی (مثل «چقدر ارسال شد») → **هم گروه لاگ، هم مشتری**.
کارت‌های حساس (خطاها و اطلاعات داخلی) → **فقط گروه لاگ**.

فهرست زیر از `bot/cards.py` استخراج شده، یعنی همه‌ی کارت‌های واقعی پروژه:

**✅ هم گروه لاگ، هم پیوی مشتری**

| کارت | چیست |
|---|---|
| `preflight_card` | قبل از ارسال: چند هدف، تخمین زمان |
| `send_started` | ارسال شروع شد |
| `live_send` | کارت زنده‌ی پیشرفت |
| `send_progress` | پیشرفت دوره‌ای |
| `send_finished` | **«چقدر ارسال شد»** — موفق/ناموفق/رد |
| `contacts_started` / `contacts_progress` / `contacts_finished` | ساخت مخاطب |
| `live_contacts` | کارت زنده‌ی ساخت مخاطب |
| `contacts_saved` | بروزرسانی مخاطبین تمام شد |
| `account_added` | اکانت اضافه شد |
| `dry_run_card` | نتیجه‌ی «تست ارسال» |

**⛔ فقط گروه لاگ — هرگز پیوی مشتری**

| کارت | چرا حساس است |
|---|---|
| `error_card` | `Trace`، `Detail`، پاسخ خام ایتا، نام موتور، فوتر `debug_line` |
| `timing_card` | تفکیک عملکرد داخلی + نام موتور |
| `pool_card` | وضعیت pool مرورگر = اطلاعات سرور |
| `contacts_probe` | جزئیات پروبِ ایمپورت |
| `peers_saved` | جزئیات داخلی peer store |
| `live_stages` | زمان مراحل + یادداشت‌های داخلی |
| `account_deleted` | فهرست فایل‌های حذف‌شده = ساختار داخلی |
| `multi_*` | ارسال چند-اکانتی مالک-only است |
| `panel_home` نسخه‌ی مالک | آمار ناوگان + ping |

### کارت خطا — دو نسخه از یک رویداد

**«کارت خطا» به مشتری نمی‌رود — ولی «خبرِ خطا» می‌رود.** مشتری باید بفهمد اکانتش درست
لاگین نشده؛ مالک باید بفهمد **چرا**.

**به مشتری:**
```
❌ اکانت اضافه نشد

شماره : 98916***736
علت   : ایتا موقتاً محدودیت گذاشته
اقدام : ۶۰ دقیقه دیگر امتحان کن

کد پیگیری : A3F9C1
```
بدون `Trace` داخلی، پاسخ خام سرور، نام موتور، نام متد، یا مسیر فایل.

**به گروه لاگ:**
```
⚠️ لاگین ناموفق
کد پیگیری : A3F9C1        ← همان کدی که دست مشتری است
مشتری     : 123456789
شماره     : 98916***736
مرحله     : code           ← کدام مرحله شکست
زمان‌ها    : browser 6s · app 4s · code 2s
کد سرور   : FLOOD_WAIT_3600
جزئیات    : <پاسخ خام ایتا>
اقدام     : یک ساعت صبر، دوباره تلاش نکن
```

**کد پیگیری حلقه‌ی وصل است:** مشتری می‌گوید «A3F9C1 خوردم»، مالک در گروه لاگ سرچ
می‌کند و کل داستان را دارد. `error_card` از قبل فیلد `Trace` را دارد.

همین تفکیک برای `paused_card`, `restriction_card`, `account_deleted` هم لازم است —
مشتری باید بداند ارسالش متوقف شد، وگرنه فکر می‌کند ربات خراب است.

**پیاده‌سازی: یک تابع واحد** `emit(event, customer_id)` که هر دو نسخه را بسازد:
```
→ گروه لاگ  : کارت کامل
→ پیوی مشتری: نسخه‌ی امن (humanize_error + کد پیگیری)
```
اگر یک‌جا باشد، دیگر امکان ندارد جای دیگری کارت کامل اشتباهاً به مشتری برود. اگر پخش
باشد، این اشتباه **حتماً** یک روز اتفاق می‌افتد.

### علت‌های لاگین به فارسی ساده

کد از قبل این‌ها را تفکیک می‌کند:

| کد داخلی | به مشتری |
|---|---|
| FLOOD روی `sendCode` | «ایتا محدودیت گذاشته — **N دقیقه** دیگر امتحان کن» ← عدد واقعی از سرور |
| کد اشتباه / منقضی | «کد درست نبود یا منقضی شد. دوباره شروع کن و کد تازه را سریع بفرست» |
| تایم‌اوت ۳۲۰ ثانیه | «کد را به‌موقع نفرستادی، لغو شد. دوباره بزن» |
| رمز دومرحله‌ای غلط | «رمز دومرحله‌ای درست نبود» |
| `sendCode` / `no_hash` | «ایتا الان کد نداد. کمی بعد امتحان کن» |
| شماره ثبت‌نشده | «این شماره روی ایتا ثبت نیست» |

⚠️ روی FLOOD **حتماً عدد واقعی** گفته شود. اگر نگوییم مشتری پشت‌سرهم تلاش می‌کند،
محدودیت ایتا را بدتر می‌کند، و آخرش ریت‌لیمیت **خودمان** مسدودش می‌کند در حالی که
تقصیر او نبوده.

## ۵) گروه لاگ

فقط کارهایی که **کاربر** انجام می‌دهد:

| رویداد | محتوا |
|---|---|
| 🟢 استارت | آیدی، نام/یوزرنیم، مشتری تازه یا برگشتی |
| ✍️ ست‌کردن متن | آیدی + **خودِ متن** |
| 📎 تعویض فایل | آیدی + نام + حجم + کپشن + **خودِ فایل** + sha256 |
| 🚀 شروع ارسال | آیدی + اکانت (ماسک) + تعداد هدف + محتوا |
| ✅ پایان ارسال | موفق / ناموفق / رد + مدت + نرخ |
| 🖼 ایمپورت تصاویر | آیدی + اکانت + تعداد عکس + جهت |
| 🧲 ساخت مخاطب | آیدی + اکانت + پیش‌شماره + هدف/ساخته‌شده |
| 🔐 لاگین | موفق، یا کارت کامل خطا (بخش ۴) |
| 🚫 مسدودی خودکار | **آیدی عددی** + تعداد اکشن + پنجره |

**تنها قاعده‌ی محدودکننده: per-recipient لاگ نشود.** ارسال به ۴۳ هزار مخاطب یعنی ۴۳
هزار پیام. فقط شروع، پایان، و پایانِ نوبتِ هر اکانت.

**sha256 فایل** مهم است: با آن می‌فهمید چند مشتری دارند یک فایل واحد را می‌فرستند.

## ۶) لاگین و پروفایل موقت

### تایم‌اوت — امروز کار می‌کند، ولی سه عدد متفاوت دارد

`bot/runner.py:1571` این را دارد:
```python
code = await asyncio.wait_for(state.code_future, timeout=300)
```
و **داخل** بلوک `async with session_pool.lease(...)` است (خط ۱۵۱۸) — پس وقتی تایم‌اوت
می‌زند، اجاره بسته می‌شود و **مرورگر واقعاً آزاد می‌شود**. نگرانی «مرورگر باز نماند» از
قبل رعایت شده.

ولی سه عدد در سه جا هست: **۳۰۰** هارد-کد (`runner.py:1571`)، **۳۵۰**
(`config.py:194`)، **۶۰۰** (`.env.example:234`، کهنه).

**تصمیم: یک متغیر واحد `MKWL_LOGIN_TTL=320` و هر سه از آن بخوانند.**

### پروفایل نیمه‌ساخته

⚠️ «پروفایل فقط بعد از لاگین موفق ساخته شود» **مستقیماً ممکن نیست**: لاگین **داخل
مرورگر** انجام می‌شود و `launch_persistent_context(user_data_dir=...)` پوشه را هنگام
لانچ می‌سازد — قبل از اینکه لاگینی اتفاق بیفتد.

و وضع امروز بدتر است: **هیچ‌چیز پروفایل را بعد از لاگین ناموفق پاک نمی‌کند**.
`delete_account_files()` فقط از `bot/app.py:992` (دکمه‌ی دستی حذف) صدا زده می‌شود. پس هر
لاگین رهاشده یک پوشه‌ی زباله می‌گذارد، و چون `list_accounts()` اسکن فایل‌سیستم است،
**آن زباله به‌عنوان یک اکانت ظاهر می‌شود**.

**راه‌حل: پروفایل موقت + ارتقا در صورت موفقیت.**
```
۱. لاگین با نام موقت:  _pending_<phone>_<random>
۲. موفق؟   →  rename به <phone>   (اتمی، همان فایل‌سیستم)
۳. ناموفق / تایم‌اوت / لغو؟  →  rmtree کامل، هیچ اثری نمی‌ماند
```
پاک‌سازی در `finally` تا روی کرش و Force-Stop هم اجرا شود، به‌علاوه یک جاروی بوت برای
`_pending_*` مانده از کرش قبلی.

۱. **کش مسدودها در حافظه.** در پروژه‌ی مرجع همان مرحله‌ی ۱ هم یک کوئری SQLite است، پس

## ۹) ریست — سه پله

پروفایل کروم دو نوع پوشه دارد، و این تفکیک کل طراحی را تعیین می‌کند:

| نوع | پوشه‌ها | حذفش چه می‌کند |
|---|---|---|
| **کش خالص** | `Cache/`, `Code Cache/`, `GPUCache/`, `DawnCache/`, `ShaderCache/`, `Service Worker/CacheStorage/` | فقط جا آزاد می‌کند. **هیچ‌کس لاگ‌اوت نمی‌شود** |
| **سشن ایتا** | `Local Storage/`, `IndexedDB/`, `Cookies`, `Preferences` | **همه لاگ‌اوت می‌شوند** |

سشن ایتا در **IndexedDB** است (`config.py` صریح می‌گوید، و همین دلیل اشتراک‌ناپذیری
contextهاست). **یعنی می‌شود گیگابایت‌ها رم و دیسک آزاد کرد بدون اینکه کسی لاگ‌اوت شود.**

| پله | کار | لاگ‌اوت؟ |
|---|---|---|
| 🧹 **۱ — پاک‌سازی سریع** | `pool.close_all()` + حذف پوشه‌های کش + پاک‌کردن قفل‌های مانده | ❌ نه |
| 🗂 **۲ — پاک‌سازی عمیق** | پله ۱ + کپچرهای قدیمی + PDFها + ledgerهای قدیمی | ❌ نه |
| 🔴 **۳ — ریست کامل** | `delete_account_files` برای همه، **با تأیید تایپی** | ✅ بله |

پله ۱ همان چیزی است که ۹۵٪ مواقع لازم است. `pool.close_all()`
(`capture/pool.py:256`) **از قبل وجود دارد**، پس نیمی از کار آماده است.

پله ۳ گزینه‌ی «فقط اکانت‌های این مشتری» هم داشته باشد.

⚠️ تله در پله ۲: **جدیدترین** کپچر باید بماند، وگرنه موتور سریع خلع سلاح می‌شود و
همه‌ی ارسال‌ها به مرورگر برمی‌گردند.

**بهتر است هیچ‌وقت لازم نشود این دکمه زده شود:**
- **نگهبان شبانه** — هر شب خودکار پله ۱.
- **آستانه‌ی دیسک** — فضای آزاد کمتر از حدی → پله ۱ خودکار + خبر.
- **آستانه‌ی رم** — رم کم شد → `pool.close_all()` خودکار.
- **کارت وضعیت منابع** در پنل مالک: رم آزاد، دیسک آزاد، تعداد مرورگر گرم، حجم
  پروفایل‌ها. `pool.status()` بخشی را از قبل می‌دهد.

⚠️ دو تله‌ی پیاده‌سازی:
- `pool.close_all()` سشن‌های **در حال استفاده** را رد می‌کند (`if entry.leased: continue`).
  ریست باید اول جاب‌ها را Force-Stop کند یا بپرسد.
- حذف کش **در حین** اجرای کروم روی همان پروفایل خطر خرابی دارد؛ اول اجاره گرفته شود.

### حساب — با سهمیه‌ی واقعی (۱۰ لاگین در روز)

چون سهمیه روی **افزودن اکانت** است، حساب مستقیماً روی مصرف مرورگر می‌افتد — که خوب
است، چون همان منبع کم است.

**بار مرورگر:**
```
۱۵ مشتری × ۱۰ لاگین = حداکثر ۱۵۰ لاگین در روز
هر لاگین: حداکثر ۳۲۰ ثانیه اشغال یک اسلات (معمولاً کمتر)
→ حداکثر ۱۵۰ × ۳۲۰ ثانیه ≈ ۱۳.۳ ساعت-مرورگر در روز

ظرفیت: ۳ اسلات × ۲۴ ساعت = ۷۲ ساعت-مرورگر در روز
→ اشغال ≈ ۱۸٪ در بدترین حالت، و عملاً حدود ۵٪
```

**بار ارسال: صفر مرورگر.** ارسال سقف روزانه ندارد ولی با موتور سریع روی HTTPS می‌رود.

مرورگر فقط برای این‌ها لازم است: لاگین، بروزرسانی مخاطبین، ساخت مخاطب، ایمپورت
تصاویر. `POOL_MAX_OPEN=3` با فاصله‌ی زیاد کافی است.

**نتیجه: ظرفیت راحت است.** صف پذیرش (فاز ۳) برای **همزمانیِ تصادفی** لازم است، نه
برای کمبود ظرفیت — یعنی وقتی ۵ نفر در یک لحظه لاگین بزنند (بخش ۱۶-۴).

### پله‌ی اول بهینه‌سازی: صفر خط کد

همه فلگ‌های موجودند که پیش‌فرض خاموش‌اند:

| تنظیم | به | سود |
|---|---|---|
| `MKWL_WARMPATH` | `1` | یک نشست از **۵ بوت** به **۱ بوت**؛ حذف شمارش ۹۸ ثانیه‌ای PV |
| `MKWL_POOL_MAX_OPEN` | `3` | روی ۱۲ گیگ |
| `MKWL_ENABLE_DIRECT` | `1` | موتور سریع را از قفل درمی‌آورد |
| `MKWL_LOGIN_TTL` | `320` | بخش ۶ |

از قبل درست‌اند (دست نزنید): `MKWL_HEADED_JOBS=False`, `MKWL_LIGHT_ASSETS=1`.

**شرط موتور سریع:** `_can_run_browserless()` (`bot/runner.py:784-817`) می‌خواهد **هر

ارسال رد می‌شود. یعنی **یک** مخاطبِ اسکرول‌شده کل مسیر سریع آن اکانت را می‌بندد.

راه‌حل: مخاطبین با **API** گرفته شوند نه اسکرول. `eitaa/contacts_list.js` همین کار را
می‌کند — یک فراخوانی، **۱٬۰۹۴ مخاطب در ۴ ثانیه**، همه با `access_hash`، در برابر
«۱۰+ دقیقه و ناقص» برای اسکرول.

قبل از اینکه مشتری با آن ارسال کند، مالک مطمئن شود کار می‌کند.

## ۱۵) اشتباهات پروژه‌ی مرجع که تکرار نمی‌کنیم

۱. **`phone UNIQUE` + انتقال بی‌صدای مالکیت** — در آن پروژه اگر مشتری B شماره‌ی مشتری A
   را اضافه کند، `ON CONFLICT(phone) DO UPDATE SET customer_id=...` **مالکیت را
   بی‌صدا منتقل می‌کند و A اکانتش را از دست می‌دهد**. جدی‌ترین مورد.
۲. **صفر تست و صفر CI.** ما ۱۶ سوئیت داریم؛ باید سبز بمانند و برای مالکیت و صف تست
   جدید اضافه شود. بزرگ‌ترین مزیت ما.
۳. **بدون WAL** و یک کانکشن به‌ازای هر فراخوانی.
۴. **بدون صف پذیرش و بدون سقف گلوبال.**
۵. **سه کپی واگرای `_gate`.**
۶. **mutex گلوبال برای ساخت مخاطب** به‌جای صف.
۷. **سشن‌ها متن ساده** در همان دیتابیسِ مستأجر که سکرت‌های زیرساخت هم آنجاست.
۸. **گارد فقط روی دکمه، نه داخل هندلر.** در آن پروژه هندلرهای پرداخت با replay
   کردن callback data قابل دسترس‌اند حتی وقتی UI خاموش است. درس عمومی: **هر کالبک
   مالک-only باید داخل خودش نقش را چک کند**، نه اینکه به نبودن دکمه اعتماد کنیم.

### ۱۶-۱) توضیح سؤال ۲ — دو فیچرِ مخاطب که اسمشان شبیه است

در کد **دو دکمه‌ی جدا** وجود دارد که هر دو در فارسی «ساخت مخاطب» ترجمه می‌شوند. سؤالم
این بود که کدامش را مشتری داشته باشد:

| دکمه | چه می‌کند | مثال |
|---|---|---|
| **`pnl:contacts`** «Build Contacts» | مشتری **یک پیش‌شماره** می‌دهد، ربات شماره‌های آن بازه را به مخاطبین اکانت اضافه می‌کند | «۰۹۱۲۳۴۵…» بده → آن بازه مخاطب می‌شود |
| **`pnl:boost`** «Contact Boost» | ربات **خودش** بلوک‌های شماره را پروب می‌کند و هر شماره‌ای که روی ایتا **ثبت‌شده** بود را مخاطب می‌کند. پیش‌شماره‌اش **تنظیم گلوبال** است و **استخر شماره‌ی مشترک** دارد تا دو اکانت یک شماره را دو بار نگیرند | خودکار می‌گردد و کاربران واقعی ایتا را پیدا می‌کند |

فرقشان: اولی **پیش‌شماره‌اش را مشتری می‌دهد**، دومی **ربات خودش می‌گردد** و از یک استخر
مشترک بین همه مصرف می‌کند.

**جواب مالک: boost به مشتری داده نشود.** پس:
- مشتری: فقط `pnl:contacts` + `pnl:save` (بروزرسانی مخاطبین)
- مالک: هر دو
- و چون boost مالک-only شد، مسئله‌ی استخر مشترک (سؤال ۱۵) خودبه‌خود حل شد

### ۱۶-۲) ارسال چند-اکانتی — سقف ۳ اکانت

مشتری می‌تواند تا **۳ اکانت** را برای یک ارسال انتخاب کند.

⚠️ یک تفکیک که باید در پیاده‌سازی رعایت شود: **«۳ اکانت انتخاب‌شده» با «۳ مرورگر
هم‌زمان» یکی نیست.**

- **تعداد اکانت انتخابی: ۳** ← این چیزی است که مشتری می‌بیند. جاب به‌ترتیب سراغ هر
  اکانت می‌رود.
- **پهنای موازی‌سازی:** `multi_parallel` (پیش‌فرض ۱، سقف ۲) — یک **تنظیم مالک** است و
  دست مشتری نیست. این تعیین می‌کند چند اکانت *در یک لحظه* کار کنند.

پس انتخاب ۳ اکانت یعنی «این ۳ اکانت در این جاب بفرستند»، نه «۳ کروم باز شود». و
`MULTI_SHARE_BUDGET` از قبل تأخیر هر اکانت را با پهنا مقیاس می‌کند تا نرخ ترکیبی
خروجی ثابت بماند.

### ۱۶-۳) دکمه پشتیبانی بدون کانال

دکمه باشد ولی کانال پشتیبانی لازم نیست. پس پیشنهادم: دکمه مستقیم **پیوی خودِ مالک** را
باز کند (`OWNER_ID` از قبل در کانفیگ هست، نیازی به لینک جدید نیست).
اگر می‌خواهید به‌جایش یک یوزرنیم دیگر باشد، فقط همان را بدهید. اگر هیچ‌کدام، دکمه
حذف می‌شود.

### ۱۶-۴) توضیح سؤال ۱۴ — آن «محدودیت» به چه مربوط است

سؤالم درباره‌ی **صف مرورگر** بود، نه سهمیه.

مرورگر منبع کم است: روی ۱۲ گیگ همزمان **۳ تا ۴** کروم بیشتر جا نمی‌شود. حالا اگر
۵ مشتری در یک لحظه «افزودن اکانت» بزنند، دو نفرشان باید **منتظر بمانند** تا یک اسلات
آزاد شود.

سؤال این بود که در آن لحظه به مشتری چه بگوییم:

| گزینه | پیام | عیب |
|---|---|---|
| الف | «۲ نفر جلوتر از تو در صف‌اند» | **لو می‌دهد که مشتری‌های دیگری هم وجود دارند** |
| ب | «سرور شلوغه، کمی بعد امتحان کن» | مشتری نمی‌داند چقدر صبر کند |
| **پ (پیشنهاد من)** | «⏳ در نوبت — تخمین ۲ دقیقه. همین‌جا منتظر بمان، خودم خبر می‌دهم.» | — |

گزینه پ هم زمان می‌دهد هم وجود بقیه را لو نمی‌دهد. **پیش‌فرض: گزینه پ.**

توجه: با اعداد واقعی این وضعیت **کم پیش می‌آید** — ۱۵ مشتری × ۱۰ لاگین = ۱۵۰ لاگین در
روز، هر کدام حداکثر ۳۲۰ ثانیه، در برابر ۳ اسلات × ۲۴ ساعت ظرفیت. یعنی حدود **۵٪
اشغال**. صف فقط برای همزمانیِ تصادفی لازم است، نه برای کمبود ظرفیت.

## پیوست — چه چیزی بررسی و رد شد

نگه داشته شده تا دلیلش گم نشود و دوباره بررسی نشود.

### الف) پورتال وب — رد شد
بررسی شد و اول پیشنهاد هم شده بود، چون `portal/` از قبل توکن مالکیت hmac، TTL، سقف کد
غلط و حساب ظرفیت دارد. **تصمیم مالک: استفاده نمی‌شود.** مشتری فقط دکمه‌ی «افزودن
اکانت» دارد و لاگین داخل تلگرام است. پوشه‌ی `portal/` در کد می‌ماند ولی وایر نمی‌شود
(`portal_enabled` خاموش). این ساده‌سازی خوبی بود: `_bridge_login_job` از قبل کل جریان
لاگین را دارد.

### ب) ورکرها / سرور دوم — لازم نیست
دلیل اولیه‌ی پیشنهادشان دو چیز بود: رم، و **تنوع IP** (چون کامنت `config.py:244-246`
می‌گوید محدودیت‌های ایتا per-account نیستند، پس همه‌ی مشتری‌ها از یک IP بیرون می‌روند و
`PEER_FLOOD` روی ناوگان جمع می‌شود).
**تصمیم مالک: IP مشکلی ایجاد نمی‌کند.** و با مقیاس ۷–۱۵ کاربر و موتور سریع، رم هم
مسئله نیست. پس **فاز ورکرها حذف شد.**
یادداشت: اگر روزی `PEER_FLOOD` دسته‌جمعی دیدید، علتش همین است و درمانش ورکر (تنوع IP)
است، نه تنظیم تأخیر. کارت `⏱ RUN TIMING` که پروژه از قبل می‌سازد خودش نشان می‌دهد.

### پ) بکاپ سشن — رد شد
پیشنهاد شده بود چون در کل پروژه **هیچ بکاپی وجود ندارد** و `eitaa/session_export.js`
قطعه‌ی لازم را دارد. **تصمیم مالک: لازم نیست.**
ریسک باقی‌مانده (یک خط): اگر دیسک از بین برود، لاگین همه‌ی اکانت‌ها می‌پرد و هر مشتری
باید اکانت‌هایش را با کد پیامکی دوباره لاگین کند.

### ت) لاگ دو لایه و پرونده‌ی ویرایش‌شونده — اختیاری شد
پیشنهاد شده بود از ترس FloodWait شدن گروه لاگ. **تصمیم مالک: حجم لاگ زیاد نیست چون
فقط کارهای کاربر لاگ می‌شود.** طرح ساده‌ی بخش ۵ جایش را گرفت. تنها قاعده‌ای که ماند:
per-recipient لاگ نشود.

### ث) موتور `direct` در UI — پنهان می‌ماند
همان hybrid منهای شبکه‌ی ایمنی است و `effective_engine()` خودش تنزلش می‌دهد. در کد
می‌ماند، از منو بیرون.
